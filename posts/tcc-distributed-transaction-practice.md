# 退款链路中的 TCC：先划清事务边界

一笔退款可能同时涉及退款单、商户账户、内部账本和外部支付渠道。讨论 TCC 之前，先问一个具体问题：这些参与方中，谁支持预留资源，谁能保证重复确认不会再次扣款？

下面以“内部账户预留退款资金”为例讨论 TCC。这里的余额指商户可用余额；这个简化模型不覆盖手续费、授信或垫资。外部支付渠道没有承诺 Try/Confirm/Cancel 接口时，不属于这笔内部 TCC 事务。

## 三个阶段，分别改变什么

假设内部账户需要预留 100 元。Try 在一个本地数据库事务中校验可用余额，将可用余额减少 100 元、冻结余额增加 100 元，并写入分支事务记录。

Confirm 将这笔冻结转为确定的资金占用或账务变更；具体科目由账务模型决定。Cancel 则释放冻结，将资金退回可用余额。Try 已经修改了资源状态，只是没有完成最终业务动作。

TCC 避免的是跨网络长时间持有数据库事务，分支内部仍需要短事务、约束和必要的行锁。冻结资源也有业务成本，不能据此直接推出“高并发下一定更快”。

## 用状态迁移约束重复和乱序请求

每个分支至少有 `TRIED`、`CONFIRMED`、`CANCELLED` 三个状态，分支键可以由全局事务 ID 与分支 ID 组成。仅用全局事务 ID 不够：一笔全局事务可能在同一个服务中有多个分支。

正常迁移只有两条：`TRIED → CONFIRMED` 和 `TRIED → CANCELLED`。已取消的分支不能再 Try，已确认的分支不能再 Cancel。相同操作重试可以返回已有结果，冲突操作应明确拒绝并触发核查。

金额、账户、币种等请求要素也要与首次请求匹配。同一个事务键携带不同金额，不能作为一次普通的幂等重试放行。

### 空回滚与迟到的 Try

调用 Try 超时，不代表 Try 一定没有执行。协调器可能先发来 Cancel，而 Try 请求仍在途中。

Cancel 发现分支不存在时，应在本地事务内写入 `CANCELLED` 记录，再返回成功。迟到的 Try 看到取消记录后拒绝预留。直接“查不到就返回”而不留记录，会让迟到的 Try 冻结一笔再也无人释放的资源。

并发时，Try 和 Cancel 都可能先读到“不存在”。因此分支键必须有唯一约束，插入竞争失败的一方应重新读取已提交的状态，按状态机决定后续动作。两次独立的存在性检查不能替代这一步。

### 幂等必须和资金变更一起提交

“先检查是否执行过，再扣余额”存在并发窗口。分支状态迁移、冻结金额变更和账务记录需要在同一本地事务里完成，并通过条件更新或行锁决定哪个请求执行。

如果本地提交后响应丢失，协调器会重试。重试读取终态并返回原结果，不再次变更余额。分支记录不能任意清理，应覆盖协调器可能重试和恢复的周期，并保留可核对的账务凭据。

## Confirm 失败后，不能随意切换为 Cancel

所有 Try 成功后，协调器应持久化全局确认决定，再通知各分支。某个 Confirm 超时或失败，通常需要继续重试确认；其他分支可能已经提交，不能因为暂时收不到响应就把整笔事务改成取消。

协调器需要可恢复的决策日志、重试与告警机制。若参与者的确认逻辑出现不可恢复的业务错误，需要人工修复和对账。TCC 并不保证所有分支在同一时刻完成，也不能消除中间状态对查询的影响。

## 外部退款放在哪里

内部资金预留成功，不等于用户已经收到退款。外部渠道调用还需要自己的业务单号、幂等约定、回调验签、主动查询和对账。

一种设计是在内部事务确认后，通过同事务保存的 outbox 任务发起渠道退款。渠道结果不确定时保留资金占用并继续查询；只有取得明确失败结果并满足业务规则后，才通过独立的账务动作释放资金。已经完成的 TCC 不应被一个迟到的 Cancel 请求改写。

这只是可选边界，实际还要结合渠道是否支持冻结、退款不可逆性和账务要求设计。把外部请求放进 Confirm 后直接等待，并不能让不支持 TCC 的渠道获得原子提交能力。

## 什么情况下值得用

如果内部资源确实可预留、业务需要提前拒绝余额不足，而且团队能维护分支状态机和协调器，TCC 才有明确的价值。仅仅因为“MQ 偶尔不一致”就换成 TCC，可能只是把可靠投递问题换成更复杂的协调问题。

不需要预留资源时，本地事务配合 outbox、幂等消费和对账可能已经足够。跨较长业务流程且有明确补偿语义时，可以评估 Saga；补偿能否执行、执行期间暴露什么状态，都需要逐项检查，不能简单认为它比 TCC 接入轻松。

验收至少覆盖重复 Try、Cancel 先到、Try 与 Cancel 并发、本地提交后响应丢失、协调器重启和外部退款结果未知。最后核对可用余额、冻结余额与账务记录，检查每一笔预留都有可追溯的去向。
