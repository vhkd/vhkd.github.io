从订单日报入手，理解一条数据链路

假设需要给运营做一张日报：按渠道统计昨天支付成功的订单数和金额。这个练习不需要一开始就部署一套大数据平台，先用数据库查询和小批量样本，就能遇到许多真正需要理解的问题。

先确定“昨天支付成功”的意思

按订单创建时间统计，会漏掉前天创建、昨天支付的订单。按支付时间统计，还需要明确时区，以及边界是否使用左闭右开区间。退款是在支付日报中回减，还是放入独立退款报表，也属于业务口径。

金额要确认币种、单位和精度。多次支付尝试中只能计入满足规则的成功记录，不能直接数支付流水行数。否则 SQL 跑得再快，结果也可能不对。

先写出几个边界样本：跨日支付、重复通知、部分退款、跨时区交易。每次调整计算方式，都用这组样本核对口径。

再画出数据经过哪里

一条最小链路可以是：业务数据库 → 增量采集 → 明细层 → 按渠道汇总 → 报表查询。

每一段都要回答两个问题：处理到哪里了，失败后从哪里继续。采集可以使用变更日志，也可以在有限场景下用更新时间窗口拉取；后者需要处理同时间戳记录、事务提交延迟和重叠窗口，不能只保存“最后一行的时间”就认为不会漏。

明细层保留订单业务键和变更版本，便于去重及重算。只保存汇总数字，后面发现统计规则有误时，就很难解释差额来自哪笔订单。

把日报改成实时看板，会多出什么问题

日报可以等一批数据到齐后计算，实时看板则需要持续更新。此时要区分事件发生时间和系统收到事件的时间。

举一个时间示例：23:59 支付的订单，00:02 才同步到计算链路。按到达时间分组会算到第二天，按支付时间分组则应修正前一天的数据。

流处理里的 watermark 用于表达事件时间推进情况，并配合窗口判断何时输出结果。它不能保证之后绝无迟到事件；超出允许迟到范围的数据，仍需要明确的侧路处理、补算或更正策略。

因此，“实时结果”往往需要说明是否暂定，以及何时完成核对。窗口结束就永远不改，和允许历史结果修正，是两种不同的产品约定。

用重跑检验链路，而不是只看第一次成功

把同一批输入处理两次，订单数是否翻倍？从中间位点重启后，会不会遗漏一段数据？修改退款口径后，能否只重算受影响的日期？

这些问题决定了主键、去重、位点和输出提交方式。框架提供的检查点或 exactly-once 能力有适用边界；如果外部输出没有事务或幂等支持，不能只凭打开一个配置就宣称端到端只算一次。

最后再选工具

当数据量和时效要求允许时，定时 SQL 或简单批任务可能已经够用。需要处理变更流、复杂窗口和持续状态时，再评估 Kafka、Flink 等组件，并给出延迟、吞吐、恢复时间和维护成本的目标。

一个有用的入门成果是：日报数字可以追溯到订单，重复输入不会重复统计，任务中断可以恢复，迟到订单有明确去向。把这条小链路做完整，后面学习组件时就知道自己要验证什么。
