# Java 服务维护：从一个退款接口检查边界

“Controller 不要写太多逻辑”很难直接指导一次改动。一个更具体的问题是：同一笔退款被调用两次时，哪个位置负责挡住重复操作？渠道超时后，哪个位置决定这笔退款还能不能重试？

以一个简化的退款接口为例，可以沿着下面几个边界检查。这里讨论结构，不涉及具体支付渠道的协议。

## 参数合法，不等于允许退款

Controller 可以处理 JSON 解析、字段格式、身份认证结果和响应映射。金额是否超过可退额度、订单是否允许退款，则需要在业务层根据权威数据判断，并在真正占用额度时处理并发竞争。

如果只在接口入口先查一次剩余额度，两个并发请求都可能通过。把查询搬进 Service 也不会自动修复问题：需要让校验与占用处于可保证一致性的操作中，例如本地事务里的条件更新，并检查受影响行数。

退款请求还需要稳定的业务幂等键。相同键、相同请求返回已有处理结果；相同键、不同金额应拒绝，而不能被当成普通重试。

## 不要把网络调用的超时当成本地回滚

一种危险的实现是：开启数据库事务、调用外部退款接口、收到超时后抛异常，最后期待所有事情都回到调用前。

本地事务可以回滚数据库操作，却撤不回渠道可能已经受理的退款。网络超时只能说明结果未取得，不能证明执行失败。

可以把“建立退款请求及待发送任务”先在本地事务中提交，再通过可靠任务调用渠道。渠道结果未知时保留处理中状态，继续查询；如何占用和释放资金，需要另行定义账务规则。这个拆分增加了中间状态，但让失败后从哪里恢复变得明确。

## 错误分类要对应调用方能做的事

余额不足、请求参数错误、数据库不可用和渠道结果未知，不应该全部返回同一个“操作失败”。它们对应的动作不同：修改请求、稍后再试、查询已有结果，或者等待人工处理。

错误响应可以包含稳定的错误码和请求关联 ID。原始异常、SQL、支付凭据不应直接返回给调用方。服务端保留异常原因，并按错误类别决定告警、重试或业务拒绝。

“可重试”也要有范围：读取超时和带幂等约定的退款重试，风险不同。没有明确幂等能力的写操作不能套用统一自动重试。

## 日志应回答一笔请求停在哪里

比起在每个方法入口打印参数，更有用的是记录状态迁移及其依据：退款单号、渠道单号、旧状态、新状态、触发来源和失败类别。

如果回调被当成重复通知跳过，日志里需要能看出依据；如果条件更新没有生效，需要知道当前状态是否已经被其他请求推进。只记录“调用成功”无法解释这些问题。

关联 ID 适合出现在日志和追踪里，退款单号不适合作为监控指标标签，否则每笔订单都会制造新的指标序列。两种可观测数据需要分开设计。

## 改完以后，验证失败路径

正常退款成功只覆盖了最顺利的一条路径。维护这类接口时，还应验证重复请求、并发占用额度、渠道超时后反查成功、本地提交后任务未发送，以及回调与查询同时到达。

这些场景能回答边界是否有效。只有把每种失败的恢复入口说明白，下一次修改接口的人才不必重新猜测哪些动作可以重做。
